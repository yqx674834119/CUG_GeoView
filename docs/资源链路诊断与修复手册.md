# 资源链路诊断与修复手册

## 1. 背景

历史上出现过以下现象：

- 上传图片后，算法执行成功，历史记录正常
- 结果文件在容器内真实存在，例如：
  - `/app/backend/static/upload/res/abc.png`
- 但浏览器访问图片 URL 失败
- 浏览器报：
  - `net::ERR_CONTENT_LENGTH_MISMATCH 200 OK`
- 容器内 `curl` 访问本机后端也会报：
  - `curl: (18) transfer closed with xxx bytes remaining to read`

这类问题的核心特征是：

- 文件系统正常
- 业务接口正常
- 真正异常发生在“静态资源 HTTP 传输链路”

当前版本已经把默认资源链路切换到新 API：

- 图片主链路：`/api/file/assets/photos/<path>`
- 图片备用链路：`/api/file/assets-buffered/photos/<path>`
- 视频链路：仍走 `/api/file/assets...` 或 `/api/file/assets-buffered...`
  - 但服务端实际强制使用应用层 `Range` 流式返回

不再建议依赖旧地址：

- `/_uploads/photos/<path>`

## 2. 新增的镜像内诊断能力

### 2.1 后端镜像

后端镜像启动时会自动执行资源链路自检。

自检内容：

- 检查后端是否成功启动：
  - `GET /api/system/ping`
- 在容器内生成探针文件：
  - `res/geoview_startup_probe.png`
  - `res/geoview_startup_probe.mp4`
- 通过本机回环地址请求以下链路并比对响应头和实际响应体长度：
  - `/api/file/assets/photos/res/geoview_startup_probe.png`
  - `/api/file/assets-buffered/photos/res/geoview_startup_probe.png`
  - `/api/file/assets/photos/res/geoview_startup_probe.mp4` with `Range`
  - `/api/file/assets-buffered/photos/res/geoview_startup_probe.mp4` with `Range`
- 额外检查旧链路：
  - `/_uploads/photos/res/geoview_startup_probe.png`
  - 该检查只记为 warning，不作为新版链路成败依据

输出位置：

- 容器日志：
  - `docker logs <backend-container>`
- JSON 诊断文件：
  - `/tmp/geoview-logs/backend-startup-diagnostics.json`
- 诊断接口：
  - `GET /api/system/diagnostics/assets`

如果新版链路检查失败，后端默认会启动失败并退出。

默认行为：

- `GEOVIEW_STARTUP_DIAGNOSTICS=true`
- `GEOVIEW_STRICT_STARTUP_DIAGNOSTICS=true`

### 2.2 前端镜像

前端镜像启动时会输出运行时配置诊断，并生成静态诊断文件。

诊断内容：

- 解析后的后端地址
- `backendAssetMode`
- 推荐资源前缀
- 旧链路前缀提示
- 关键配置是否合法

输出位置：

- 容器日志：
  - `docker logs <frontend-container>`
- 静态诊断文件：
  - `/runtime-diagnostics.json`

默认会校验：

- `GEOVIEW_BACKEND_ASSET_MODE` 必须是：
  - `buffered`
  - `sendfile`
  - `chunked`
- 必须能解析出后端目标地址

默认行为：

- `GEOVIEW_STRICT_RUNTIME_DIAGNOSTICS=true`

## 3. 如何查看诊断结果

### 3.1 后端

查看后端启动期诊断日志：

```bash
docker logs <backend-container> | grep '\[diag\]\[backend\]'
```

查看诊断 JSON：

```bash
docker exec <backend-container> cat /tmp/geoview-logs/backend-startup-diagnostics.json
```

查看诊断接口：

```bash
curl -sS http://127.0.0.1:5008/api/system/diagnostics/assets
```

### 3.2 前端

查看前端运行时诊断日志：

```bash
docker logs <frontend-container> | grep '\[diag\]\[frontend\]'
```

查看前端静态诊断文件：

```bash
curl -sS http://127.0.0.1:3000/runtime-diagnostics.json
```

## 4. 诊断结果解释

### 4.1 后端 `pass=true`

说明：

- 后端本机回环访问图片链路正常
- `Content-Length` 与实际返回长度一致
- 视频 `Range` 响应正常
- 当前镜像内部没有复现历史上的截断问题

这种情况下，如果集群里仍然访问失败，优先怀疑：

- 网关 / Ingress / 反向代理篡改了传输
- 平台路径重写错误
- 前端仍在使用旧的 `/_uploads/...` 地址

### 4.2 后端 `pass=false`

说明：

- 问题已经在容器内本机回环阶段复现
- 这不是前端问题，也不是外部网关问题
- 当前后端镜像不应继续交付

重点看这些字段：

- `image_direct`
- `image_buffered`
- `video_direct_range`
- `video_buffered_range`
- `errors`

如果看到：

- `body_length_matches_header=false`

说明：

- 典型的“声明长度与实际传输长度不一致”
- 需要优先检查服务端返回方式或中间代理截断

### 4.3 后端 warning 提示旧链路异常

如果只看到：

- `legacy _uploads route is not healthy`

但新版链路全部通过，说明：

- 旧 `/_uploads/...` 路由仍然不可靠
- 当前部署必须统一使用新 API

这不是新版交付链路失败，但说明：

- 前端或历史记录中一旦混入旧 URL，仍可能再次触发老问题

### 4.4 前端 `runtime-diagnostics.json`

重点看：

- `resolvedBackendUrl`
- `backendAssetMode`
- `preferredAssetPrefix`
- `status`

如果：

- `status=invalid`

说明：

- 前端运行时配置本身就不合法
- 不需要先查业务接口，先修前端容器环境变量

## 5. 常见修复方式

### 5.1 前端仍然在请求 `/_uploads/photos/...`

修复方式：

- 前端必须统一走新的资源地址转换逻辑
- 历史记录里的图片、mask、视频都应落成：
  - `/api/file/assets/photos/...`
  - 或 `/api/file/assets-buffered/photos/...`

不要继续依赖：

- `/_uploads/photos/...`

### 5.2 集群里出现 `ERR_CONTENT_LENGTH_MISMATCH`

先分层判断：

1. 看后端启动诊断是否 `pass=true`
2. 如果后端自检通过，再看集群网关链路

需要重点确认：

- 平台是否对响应做了二次缓冲
- 是否有错误的 `Content-Length` 重写
- 是否对大文件/图片做了不完整压缩
- 是否对 `Range` 请求处理异常

### 5.3 前端容器配置错误

前端部署时必须显式设置：

- `GEOVIEW_BACKEND_URL`
- `GEOVIEW_BACKEND_ASSET_MODE=buffered`

集群默认推荐：

- `GEOVIEW_BACKEND_URL=http://172.20.20.240:31839/186/5008`
- `GEOVIEW_BACKEND_ASSET_MODE=buffered`

### 5.4 后端上传目录或结果目录配置错误

后端必须确保：

- `UPLOADED_PHOTOS_DEST=/app/backend/static/upload`
- 结果目录实际写入：
  - `/app/backend/static/upload/res`

如果目录不存在、不可写、被错误挂载，诊断脚本通常会直接失败。

### 5.5 必须临时关闭严格诊断

默认不建议关闭。

如果需要临时放行，可设置：

```bash
GEOVIEW_STRICT_STARTUP_DIAGNOSTICS=false
GEOVIEW_STRICT_RUNTIME_DIAGNOSTICS=false
```

但这只适合临时排障，不适合作为最终交付配置。

## 6. 建议的交付验收动作

交付前至少做以下检查：

1. 看后端容器日志里是否出现：
   - `[diag][backend] pass=True`
2. 调用：
   - `GET /api/system/diagnostics/assets`
3. 看前端容器日志里是否输出：
   - `resolved_backend_url`
   - `backend_asset_mode`
4. 访问：
   - `/runtime-diagnostics.json`
5. 确认前端所有图片/视频请求都不再落到：
   - `/_uploads/photos/...`
