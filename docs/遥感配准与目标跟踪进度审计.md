## 2. 当前总体判断

### 2.1 总体状态

这 2 个功能域都已经不再停留在“只有页面入口或只有说明文档”的状态，而是存在真实的前后端改造，且当前本地 `HEAD` 相比远端主干已经形成了两条较完整的工程闭环：

- 配准：前端双列表上传与自动配对、后端批量逐对执行、结果回显、成功结果入库，这条链路已经基本打通。
- 跟踪：前端图像序列上传与首帧框选、后端单目标跟踪执行、预览图/视频/轨迹 JSON 输出、历史页视频打开与下载，这条链路已经基本打通。

但这两块都还没有达到“完全收口”状态，主要仍有以下共性缺口：

- 自动化测试和端到端自检证据不足。
- Docker 文件本身未改，但依赖同步依赖重新构建镜像才能生效。
- 历史页只消费了部分结果资产，没有把所有新产出都完整展示出来。
- 文档存在“新实现说明”与“旧诊断文档”并存的情况，其中部分诊断内容已经被当前代码修复，文档口径并不完全一致。

### 2.2 进度结论

- 遥感影像配准：`基本完成，属于工程基线可用状态`
- 遥感目标跟踪：`基本完成，属于工程基线可用状态`

这里的“基本完成”指的是前后端协议、主要输出、历史入库与页面结果展示已形成闭环；不代表遥感算法能力、部署验证和自动化回归已经全部完成。

## 3. 遥感影像配准

### 3.1 本功能域涉及的改动文件

- `backend/applications/api/analysis.py`
- `backend/applications/api/model.py`
- `backend/applications/interface/analysis.py`
- `backend/applications/interface/hf_registration.py`

- `frontend/src/views/history/History.vue`
- `docs/REGISTRATION_REIMPLEMENTATION_PLAN.md`
- `docs/CODEX_BACKEND_TRACKING_REGISTRATION_DIAGNOSIS.md`
- `backend/requirements-hf.txt`

### 3.2 已完成内容

- 前端页面已从原先“直接拼 `FormData` 猜测后端如何接收”的状态，重构为两段式流程：
  - 先通过 `/api/file/upload` 上传两组影像
  - 再以 JSON 调用 `/api/analysis/registration`
- 注册页已经支持：
  - 参考影像 / 待配准影像双列表上传
  - 同名优先、顺序回退的自动配对预览
  - 配对失败提示
  - 模型选择
  - 成功 / 失败分批展示
  - 结果图、叠加图、棋盘图下载
- 后端 `registration_api()` 已正式接收：
  - `model_path`
  - `list: [{ first, second, pair_name, pairing_strategy }]`
- 后端 `applications/interface/analysis.py` 已把 `model_path` 继续向下传给注册执行器，并在成功时写入历史记录。
- `backend/applications/interface/registration.py` 已实现新的批量逐对执行逻辑：
  - 逐对读取 fixed / moving
  - 每对失败不会中断整批
  - 成功结果返回 `output_path / overlay_path / checkerboard_path`
  - 同时返回 `method_used / transform_type / match_count / inlier_count / inlier_ratio / rmse`
- 配准执行策略已经实际做成三类入口：
  - `builtin:registration:auto`
  - `builtin:registration:opencv`
  - `hf:kornia/loftr`
- 当前代码中真实存在的算法路径包括：
  - Kornia LoFTR 直接匹配
  - 外部 `hf_registration.py` 子进程 LoFTR
  - OpenCV SIFT/ORB/AKAZE + RANSAC 兜底
- 配准结果已经接入历史记录入库：
  - `before_img` = fixed
  - `before_img1` = moving
  - `after_img` = registered moving
  - `data` = 配准元数据 JSON

### 3.3 已实现的前后端契约与输出路径

当前配准接口契约已经在代码中落地：

请求：

```json
{
  "model_path": "builtin:registration:auto",
  "list": [
    {
      "first": "/_uploads/photos/fixed_a.tif",
      "second": "/_uploads/photos/moving_a.tif",
      "pair_name": "fixed_a__moving_a",
      "pairing_strategy": "同名匹配"
    }
  ]
}
```

成功响应结构：

```json
{
  "code": 0,
  "msg": "配准完成，共 x/y 对成功",
  "data": {
    "results": [
      {
        "status": "success",
        "pair_name": "...",
        "fixed_input": "/_uploads/photos/...",
        "moving_input": "/_uploads/photos/...",
        "output_path": "/_uploads/photos/res/...",
        "overlay_path": "/_uploads/photos/res/...",
        "checkerboard_path": "/_uploads/photos/res/...",
        "method_used": "...",
        "transform_type": "...",
        "match_count": 0,
        "inlier_count": 0,
        "inlier_ratio": 0.0,
        "rmse": 0.0
      }
    ],
    "summary": {
      "total_pairs": 0,
      "success_pairs": 0,
      "failed_pairs": 0,
      "model_path": "..."
    }
  }
}
```

输出路径规则已经在代码中实现：

- 上传输入前缀：`/_uploads/photos/`
- 结果输出前缀：`/_uploads/photos/res/`
- 物理目录：
  - `static/upload/`
  - `static/upload/res/`
- 结果文件名模式：
  - `registration_{pair_name}_registered.png`
  - `registration_{pair_name}_overlay.png`
  - `registration_{pair_name}_checkerboard.png`
- 最终文件名前会再加 `md5` 随机前缀，避免重名

### 3.4 部分完成内容

- 历史页对“自动配准”的基本预览仍沿用旧的三图模式：
  - 原图 1 = fixed
  - 原图 2 = moving
  - 结果图 = registered
- 虽然后端已经把 `overlay_path` 和 `checkerboard_path` 写入 `data` 元数据，但当前历史页并没有消费这两个路径，因此：
  - 注册页即时结果页能看叠加图/棋盘图
  - 历史页暂时不能直接打开这两类复核结果
- 当前输出以可视化结果为主，代码与文档都明确没有保证保留原始 GeoTIFF 地理参考。
- 文档层面已经新增了 `docs/REGISTRATION_REIMPLEMENTATION_PLAN.md`，但同时仓库里还存在一份 `docs/CODEX_BACKEND_TRACKING_REGISTRATION_DIAGNOSIS.md`。这份诊断文档描述的是更早阶段的问题，其中“前后端协议完全不匹配”“模型路径未向下传递”等结论，与当前 `HEAD` 已不完全一致，因此文档口径属于部分过时。

### 3.5 仍缺失 / 风险点

- 当前实现更接近“切片级二维图像配准工程基线”，而不是完整遥感几何配准流水线。
- 仍未接入 SNAP、AROSICS、pyroSAR 等更重的遥感专用配准链路。
- 对超大幅面、多时相、多模态、复杂几何差异场景的稳定性，没有在当前未推送提交中看到自动化验证证据。
- 没有新增回归测试来覆盖：
  - 双列表上传后 JSON 调用
  - 批量部分失败
  - 历史记录元数据
  - 结果路径可访问性
- 配准依赖同时分布在主服务环境与 `HFPyTorch310` 环境之间：
  - 主服务环境主要负责页面请求与 OpenCV 路径
  - LoFTR 还可能依赖外部子进程环境
  - 这意味着部署环境一致性仍有要求

### 4.4 部分完成内容

- 历史页虽然已经支持打开 / 下载结果视频，但还没有把 `trajectory_path` 暴露成可直接下载或可视化的入口。
- 历史页展示的仍然是：
  - 原图 = 首帧
  - 结果图 = 预览图
  - 视频 = 单独按钮打开
  这意味着轨迹 JSON 目前只在即时结果页中有下载入口。
- 当前实现只支持**单目标**，且必须由用户在首帧手工框选初始框。
- 当前输入已经明确收敛为“图像序列”，不是视频上传链路；这比旧实现真实，但功能边界也明显比“全域目标跟踪与预警”窄。

### 4.5 仍缺失 / 风险点

- 没有多目标关联、ID 管理、重识别、异常预警逻辑。
- 目前更准确的描述是“遥感图像序列单目标跟踪工程基线”，不能等同于完整的全域预警系统。
- 跟踪器主路径依赖 `opencv-contrib-python` 提供的 tracker API；如果部署环境只安装普通 `opencv-python`，将退化到模板匹配，鲁棒性会下降。
- 本地未推送改动中没有新增端到端自动化测试或回归脚本来证明：
  - 首帧框选坐标映射
  - 结果视频可播放
  - JSON 轨迹结构稳定
  - 历史页视频链接可访问
