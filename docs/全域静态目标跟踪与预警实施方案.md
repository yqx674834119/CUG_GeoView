# 全域静态目标跟踪与预警实施方案

## 1. 现状审计

结合当前代码，现有跟踪模块的实际能力如下：

1. 前端入口是 `frontend/src/views/mainfun/Tracking.vue`，要求用户上传按时间顺序命名的图像序列，并在首帧手工框选一个目标。
2. 后端主逻辑在 `backend/applications/interface/tracking.py`，核心是 `CSRT / KCF / MIL + 模板匹配纠偏`。
3. 当前输出是预览图、结果视频、轨迹 JSON 和简单统计摘要。

这说明现有实现是一个“单目标连续跟踪工程基线”，不是你现在要求的“全域静态目标跟踪与预警”。

它与目标需求的主要差距有：

1. 不是全域：当前只能跟一个手工初始化目标，不能对整幅时序影像里的目标进行全域发现、关联和统一编号。
2. 不是静态目标时序建模：当前假设目标在连续帧中运动，缺少“跨时相持续存在、出现、消失、扩张、迁移”的静态目标建模。
3. 没有环境上下文融合：没有把配准、地物分割、变化检测等已有能力真正串成时序分析 pipeline。
4. 没有预警子模块：目前只有轨迹结果，没有异常事件定义、分级规则、趋势判断和告警输出。
5. 没有面向 `MOTA / IDF1 / 异常 Precision` 的评估闭环。

结论：当前实现不能直接支撑本次指标要求，但很适合作为“已有工程基线方案”保留。

## 2. 推荐结论

我建议优先采用：

**方案 A：复用现有模型，构建完整 pipeline。**

原因：

1. 与你当前仓库最兼容，改动范围最可控。
2. 可直接复用你已经接好的配准、检测、分割、变化检测能力。
3. 更适合“先审查方案，再执行落地”，不会把项目一下子带进新的重依赖栈。
4. 可以把现在的单目标跟踪保留为“工程基线/对照方案”，新方案单独挂到前端，不影响其他模块。

同时保留：

**方案 B：接入开源多目标跟踪方案。**

它适合作为第二阶段增强或对照实验，不建议作为第一落地点。

## 3. 方案 A：复用现有模型构建完整 Pipeline

### 3.1 总体目标定义

这里我建议把“全域静态目标跟踪”重新定义为：

> 在已经按时间排序的多时相影像或准视频序列上，对整幅图中的目标进行自动发现、跨时相关联、统一 ID 管理，并基于历史轨迹与场景上下文输出趋势预警。

这样定义后，`MOTA / IDF1` 仍然成立，因为它们本质上是在评估“检测 + 关联 + ID 保持”。

### 3.2 复用你仓库中已有能力

可直接复用的现有模块如下：

1. 配准：`backend/model/registration/auto`
2. 目标检测：
   - `backend/model/object_detection/mmrotate_oriented_rcnn_r50_fpn_1x_dota_le90`
   - `backend/model/object_detection/paddle_yolo`
   - `backend/model/object_detection/hf_waldo30`
3. 语义分割：
   - `backend/model/semantic_segmentation/mmseg_cugrs`
   - `backend/model/semantic_segmentation/paddle_deeplabv3p`
4. 变化检测：`backend/model/change_detection/bit_256x256`

### 3.3 推荐主链路

推荐主链路如下：

1. 输入阶段
   - 输入按时间排序的多时相影像序列。
   - 不再要求用户手工框首帧目标。
   - 前端只负责上传序列、选择“方案 A”并设置目标类别、预警阈值、最小面积、时序窗口。

2. 影像标准化阶段
   - 复用现有 TIFF/多波段读取逻辑。
   - 统一做稳健归一化、尺寸约束和元数据抽取。
   - 保留每一时相的原始分辨率和缩放比例，供回写结果使用。

3. 时序配准阶段
   - 使用 `registration:auto` 将每个时相对齐到参考时相。
   - 输出每一时相相对参考帧的变换矩阵。
   - 后续所有目标关联都在配准后的统一坐标系中完成。

4. 全图目标发现阶段
   - 对每个时相全图运行目标检测。
   - 优先使用 `mmrotate` 检测细长/旋转目标，如飞机、船只、列车。
   - 对普通小目标场景可保留 `PPYOLO / WALDO30` 作为对照或补充候选。
   - 输出每一时相的目标框、类别、置信度、面积、方向角。

5. 场景上下文提取阶段
   - 对每一时相运行语义分割，得到水体、道路、建筑、林地、裸地等上下文图层。
   - 对每一对相邻时相运行 BIT 变化检测，得到变化热区。
   - 为每个目标附加上下文特征：
     - 所在语义类别
     - 周边语义比例
     - 是否落入变化热区
     - 与道路/岸线/建筑边界的空间关系

6. 跨时相关联阶段
   - 在配准统一坐标系中，对相邻时相目标进行 Hungarian 匹配。
   - 关联代价建议由以下部分组成：
     - 几何 IoU
     - 中心点距离
     - 类别一致性
     - 面积变化率
     - 方向角差异
     - 简单外观特征相似度
     - 上下文一致性
   - 当关联成功时，维持同一 track id；当连续多时相未匹配时，标记为消失；当新目标稳定出现超过阈值时，标记为新生目标。

7. 趋势预警阶段
   - 不建议第一版就上重型时序大模型。
   - 第一版用“规则引擎 + 滑窗统计 + EWMA/CUSUM”即可落地，且更容易把 Precision 调到 0.65 以上。
   - 预警事件建议先做以下 6 类：
     - 新增：历史不存在，连续出现 N 个时相
     - 消失：历史存在，连续缺失 N 个时相
     - 扩张：面积增长率超过阈值
     - 收缩：面积下降率超过阈值
     - 位置异常：配准后位置偏移超过阈值
     - 上下文异常：例如船落到陆地、车辆落到水面、建筑跨越禁入区域
   - 趋势预警建议输出：
     - 告警级别
     - 告警原因
     - 触发时相
     - 支撑证据
     - 历史趋势曲线

8. 输出阶段
   - 输出对象级时序轨迹 JSON
   - 输出全局告警 JSON
   - 输出目标级截图和全局预警热区图
   - 输出可供历史页和专题页复用的结构化结果

### 3.4 为何这条链路是可行的

因为它不依赖你仓库之外的核心模型能力，真正新增的只有三类工程逻辑：

1. 全图检测结果的时序关联器
2. 上下文特征抽取与融合器
3. 规则化预警引擎

这三部分都属于可控的 Python 工程实现，不需要先训练一个新的大模型才能启动。

## 4. 方案 B：接入开源多目标跟踪方案

### 4.1 候选方案

可选的成熟开源方案有：

1. ByteTrack
   - 官方仓库：<https://github.com/ifzhang/ByteTrack>
2. BoT-SORT
   - 官方仓库：<https://github.com/NirAharon/BoT-SORT>

BoT-SORT 官方 README 明确给出其在 MOT17 上达到 `80.5 MOTA / 80.2 IDF1` 量级，说明它的多目标关联框架本身是成熟的，但这是通用视频结果，不代表在卫星视频或多时相遥感影像上可直接复现。

### 4.2 这条路的优点

1. 多目标 ID 关联能力成熟。
2. 对 `MOTA / IDF1` 指标天然友好。
3. 可以直接复用现成评估脚本和结果格式。

### 4.3 这条路的缺点

1. 需要引入新的训练/推理依赖栈。
2. 通常默认面向地面视频，直接迁移到遥感小目标并不稳。
3. 仍然需要你现有的配准、上下文融合、异常预警模块做二次开发。

结论：方案 B 适合做第二阶段增强或对照实验，不适合当前作为第一落地版本。

## 5. 数据集方案

## 5.1 结论先行

没有单一公开数据集能同时完美覆盖：

1. 遥感/卫星时序目标跟踪
2. `MOTA / IDF1`
3. 目标级异常预警标签

因此建议采用“两类公开数据集 + 一类业务验证集”的组合方式。

### 5.2 跟踪指标主数据集：VISO / SatVideoDT

首选数据集：

1. VISO 官方仓库：<https://github.com/QingyongHu/VISO>
2. SatVideoDT 官方挑战页：<https://satvideodt.github.io/>

选择理由：

1. VISO 是公开的卫星视频检测与跟踪数据集。
2. SatVideoDT Track 3 明确采用 `MOTA` 和 `IDF1` 作为多目标跟踪评价指标。
3. 这是与你需求最接近的公开“遥感/卫星 + 跟踪 + MOT 指标”数据源。

已确认的官方信息：

1. VISO 官方 README 写明其包含 40 个 Jilin-1 卫星视频、`853,911` 个标注实例。
2. SatVideoDT 官方页面写明其 Track 3 基于 VISO，并使用 `MOTA` 与 `IDF1` 排名。

用途：

1. 用于验证全域检测、跨帧关联、ID 保持能力。
2. 用于打 `MOTA / IDF1` 主指标。

### 5.3 遥感跟踪补充数据集：OOTB

官方仓库：

1. OOTB：<https://github.com/YZCU/OOTB>

选择理由：

1. OOTB 是卫星视频单目标跟踪基准。
2. 它能帮助你验证卫星小目标、旋转目标、弱纹理目标的鲁棒性。
3. 虽然它不是多目标 `MOTA / IDF1` 数据集，但适合做补充回归测试。

### 5.4 备用时序影像数据集：VisDrone-MOT

官方仓库：

1. VisDrone：<https://github.com/VisDrone/VisDrone-Dataset>

选择理由：

1. 它不是卫星视频，但属于俯视/低空时序影像。
2. 官方明确提供多目标跟踪任务和公开下载。
3. 当卫星数据训练成本高或样本量不足时，可以作为工程联调和算法预训练的备用集。

### 5.5 预警指标数据集：A2Seek

官方页面：

1. A2Seek：<https://hayneyday.github.io/A2Seek/>

选择理由：

1. 它是公开的 aerial anomaly understanding 数据集。
2. 官方页面明确写明包含异常类别、帧级时间戳、区域框和原因说明。
3. 它更适合验证“异常事件检出 Precision”，尤其适合前期把预警模块单独打通。

需要说明：

1. A2Seek 是无人机场景，不是卫星视频。
2. 它可以验证“预警能力”，但不能替代 VISO 的跟踪评估。

### 5.6 最终验收数据建议

公共数据集只能做能力验证，最终验收建议这样做：

1. 用 `VISO / SatVideoDT` 验证 `MOTA / IDF1`
2. 用 `A2Seek` 验证异常事件检出能力
3. 从你的业务数据中抽 20 到 50 条真实时序样本，人工补最少量事件标签，形成内部 `GeoView-Alert-Val`

这样最稳，也最接近真正上线前的验收方式。

## 6. 详细实施步骤

下面是推荐的执行顺序。

### 阶段 0：方案挂前端，先不改后端主逻辑

目标：

1. 在前端跟踪页展示两个待审查方案：
   - 方案 A：复用现有模型构建全域静态目标跟踪与预警
   - 方案 B：接入开源多目标跟踪方案
2. 保持禁用，不影响当前可运行模型。

这一步已经适合现在先做，因为你明确要求先审查方案再执行。

### 阶段 1：新增后端全域 pipeline，不替换旧 tracking

建议新增独立模块，而不是直接重写现有 `tracking.py`。

建议新增：

1. `backend/applications/interface/tracking_global.py`
2. `backend/applications/interface/tracking_alert.py`
3. `backend/applications/interface/tracking_association.py`

理由：

1. 保留当前单目标实现作为基线
2. 降低回归风险
3. 方便前端把“工程基线”和“全域方案”并存

### 阶段 2：做全域目标发现

1. 复用你现有目标检测接口
2. 对每一时相全图推理
3. 保存原始检测框与类别
4. 给后续关联器提供统一结构：

```json
{
  "frame_index": 3,
  "timestamp": "2024-06-11",
  "detections": [
    {
      "bbox": [x, y, w, h],
      "score": 0.93,
      "label": "ship",
      "angle": 18.2,
      "area": 154.0
    }
  ]
}
```

### 阶段 3：做时序配准与统一坐标

1. 先对每个时相与参考时相做配准
2. 把所有检测结果映射到统一坐标系
3. 存储每帧变换矩阵

这是整条链路能否稳定的关键步骤。

### 阶段 4：做多时相关联

1. 以相邻时相为主做关联
2. 用 Hungarian 做全局匹配
3. 关联代价建议如下：

```text
cost =
0.35 * (1 - IoU)
+ 0.20 * normalized_center_distance
+ 0.15 * area_change_penalty
+ 0.10 * angle_penalty
+ 0.10 * appearance_penalty
+ 0.10 * context_penalty
```

4. 未匹配的稳定新目标生成新 ID
5. 连续缺失超过阈值的目标结束轨迹

### 阶段 5：做预警引擎

第一版直接上规则即可：

1. 目标新增
2. 目标消失
3. 目标面积异常增长
4. 目标面积异常收缩
5. 目标位置异常偏移
6. 目标上下文冲突
7. 区域目标密度突然升高
8. 同类目标持续聚集

建议输出：

```json
{
  "event_id": "alert_0001",
  "track_id": "ship_018",
  "event_type": "context_conflict",
  "level": "high",
  "start_frame": 8,
  "end_frame": 10,
  "evidence": {
    "context": "land",
    "expected_context": "water",
    "change_score": 0.81
  }
}
```

### 阶段 6：做评估闭环

1. 跟踪评估：
   - `MOTA`
   - `IDF1`
2. 预警评估：
   - `Precision`
   - 可同时记录 `Recall / F1`

建议验收门槛：

1. `MOTA >= 0.70`
2. `IDF1 >= 0.70`
3. `异常 Precision >= 0.65`

### 阶段 7：前端与历史页接入

执行落地时建议只改以下几个地方：

1. `frontend/src/views/mainfun/Tracking.vue`
2. `backend/applications/api/model.py`
3. `backend/applications/api/analysis.py`
4. `backend/applications/interface/analysis.py`
5. 新增的 `tracking_global*.py`

这样可以把改动面收得比较小。

## 7. 前端方案选项建议

前端建议保留三类选项：

1. 现有工程基线
   - 单目标，手工初始化，当前已可运行
2. 方案 A
   - 复用现有模型构建全域静态目标跟踪与预警
   - 推荐
3. 方案 B
   - 接入开源多目标跟踪方案
   - 备选

在你审查通过之前，方案 A/B 都应该显示为“待审查、不可执行”。

## 8. 推荐实施顺序

我建议按下面顺序执行：

1. 先保留当前单目标跟踪不动，作为基线
2. 先实现方案 A 的最小闭环：
   - 配准
   - 全图检测
   - 跨时相关联
   - 规则预警
3. 用 `VISO / SatVideoDT` 打 `MOTA / IDF1`
4. 用 `A2Seek` 打异常 Precision
5. 最后再决定是否需要方案 B 做增强
